# Feed timeline rollout

1. Run `npm run appwrite:provision-012` to compare the live schema with the captured baseline, then `npm run appwrite:provision-012 -- --apply` for the reviewed additive changes. The API and frontend configs differ from the live project in existing permissions and other attributes; do not use `appwrite push all` or `appwrite push tables`. Keep the existing table permissions until the write pause in step 2. Wait for all indexes to become available.
2. Before the write pause, run `npx ts-node -r tsconfig-paths/register scripts/revoke-client-row-writes.ts` to review existing row permissions. During the pause, revoke table-level client `create`, `update`, and `delete` permissions from the affected source and derived tables (`z_entries_read` and `zcoin_transactions` included) using the schema configurations, then rerun the script with `--apply`. This strips row-level write grants while preserving read grants. Rows in `game_comments` have `rowSecurity: false`, so its table permission change is sufficient.
3. Deploy the API and frontend together, then disable the Appwrite `timeline`, `entry-sync`, and `comments/on-create` webhooks. All social writes now go through authenticated API endpoints. Browser tabs running the old frontend must reload before writing again.
4. Run `npx ts-node -r tsconfig-paths/register scripts/reconcile-unprocessed-entries.ts` to count unprocessed `z_entries`, then rerun with `--apply`. Pause API writes while applying it. The command reports older pending rows whose owner/game already has a newer processed row; `--apply` exits without changing anything in that case. Repair those histories with a full chronological rebuild or manual correction before retrying. Successful sync marks each processed row and can be resumed after interruption.
5. Run `npm run social:backfill-feed` to count historic rows, then `npm run social:backfill-feed -- --apply`. Run `scripts/backfill-achievements.ts` in dry-run mode and then with `--apply`. Run `scripts/backfill-playtime-stats.ts` in dry-run mode; use `--apply` only when historical playtime exists and writes to the aggregates are paused. Inspect `outbox_events` with status `FAILED` and resolve them before completing the release.
6. Verify through a user JWT that direct writes to the affected tables are denied while expected reads continue to work. Check a new entry, rating, comment, list change, follow and unfollow in the API and feed. Existing frontend tabs must reload after cutover.

The API writes source rows and outbox events atomically. The worker projects feed and achievements with retries, so the feed can update shortly after the write response. Following someone projects their existing activity; unfollowing invalidates the cache immediately and feed reads enforce the current connection. Redis entries expire after 45 seconds, and the endpoint queries Appwrite if Redis is unavailable.
