# Feed timeline rollout

1. Run `npm run appwrite:provision-012` to compare the live schema with the captured baseline. Apply only reviewed additive changes with `npm run appwrite:provision-012 -- --apply`, if any remain, and wait for indexes to become available. Repository configs differ from the live project; do not use `appwrite push all` or `appwrite push tables`.
2. Publish the temporary maintenance frontend and freeze client writes to database `app`. Disabling the database blocks client SDK access but does not stop API keys, so verify source activity is stable and account for API workers and webhooks. Disable the legacy `timeline`, `entry-sync`, and `comments/on-create` webhook integrations before restoring user traffic. Capture and verify the complete backup with `node scripts/capture-release-backup.cjs <new-backup-directory>`.
3. Follow [the historical reconciliation policy](entry-reconciliation-policy.md). Generate a manifest with `npx ts-node -r tsconfig-paths/register scripts/apply-entry-reconciliation.ts --plan-out <new-manifest.json>`, review its changes and blockers, then run the same command with `--apply <manifest.json>`. It reconstructs pending groups, corrects derived counters, preserves source content, ledger and balances, and marks pending entries only after projection repairs. Require the final `status: verified` output. Do not replay these historical entries with `scripts/reconcile-unprocessed-entries.ts --apply`; null `processedAt` does not establish missing rewards.
4. After reconciliation verification, run `node scripts/revoke-release-client-writes.cjs <verified-backup-directory>` to review table and row write grants, then repeat with `--apply` while client access is disabled. The script preserves reads and row data. Audit live grants afterward, including rows created since the backup. Synchronize the schema configs to the resulting permissions without pushing unrelated schema differences.
5. Run `npm run social:backfill-feed` and `scripts/backfill-achievements.ts` in dry-run mode, then apply the reviewed plans to include activity since the initial backfill. Run `scripts/backfill-playtime-stats.ts` in dry-run mode; apply only if historical playtime requires corrections. Inspect failed outbox events and distinguish pre-existing failures from release processing failures. The achievements backfill may grant eligible badges and coins through its own idempotent rules; historical entry reconciliation itself never grants or debits coins.
6. Merge the reviewed API release before triggering its build. The frontend release can be published first with its release-readiness gate: it remains in maintenance until `/health/release` reports `social-writes-v1`, successful readiness checks, and an enabled `app` database. Keep client access disabled until the database checks and permission audit pass. Verify the new API build is serving before restoring access and confirming the public frontend opens. Existing tabs must reload.
7. Through a user JWT, verify direct writes are denied while expected reads work. Check new entry, rating, comment, list change, follow and unfollow through the API; verify feed, aggregates, annual progress and outbox processing. Record deployment evidence and final data checks in [the execution log](appwrite-012-production-execution.md).

The API writes source rows and outbox events atomically. The worker projects feed and achievements with retries, so the feed can update shortly after the write response. Following someone projects their existing activity; unfollowing invalidates the cache immediately and feed reads enforce the current connection. Redis entries expire after 45 seconds, and the endpoint queries Appwrite if Redis is unavailable.
